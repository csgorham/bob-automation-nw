# Devin's Experience — Before and After IBM Bob

This document maps the developer journey of **Devin**, a mid-level cloud developer at an enterprise insurance company, through the Golden Workflow lifecycle. It contrasts the traditional infrastructure process with the Bob-assisted experience at every stage.

---

## Who is Devin?

Devin owns application feature delivery. He has working knowledge of AWS and can read Terraform, but he is not an infrastructure specialist. He depends on a central platform team for anything that touches security groups, IAM, Vault, or CI/CD pipeline configuration. His priorities are:

1. Ship features quickly.
2. Not get paged at 2 AM.
3. Not fail a compliance review two days before release.

He is **not** trying to become a Terraform expert.

---

## The Four Friction Points in Devin's Old World

Before Bob, Devin's path through the infrastructure lifecycle looked like this:

```
Feature request
    │
    ▼
[JIRA Ticket: Add Prometheus port]
    │ wait 2 days
    ▼
[Infra team adds port, opens PR]
    │ wait for review
    ▼
[Devin pushes code]
    │
    ▼
[CI pipeline runs Sentinel] ← FAILS (wrong tag format)
    │ fix and retry
    ▼
[Prod deploy succeeds]
    │
    │ (3 weeks later)
    ▼
[2 AM page: Apache is down]
    │ SSH debug 45 min
    ▼
[Manual restart, no audit trail]
```

**Pain points at each step**:
1. **Ticket queues** — multi-day wait for infrastructure changes he could describe in one sentence.
2. **Late policy failure** — Sentinel failures discovered in CI/CD, not in his IDE.
3. **Static credentials risk** — local `.env` files with AWS keys that someone inevitably commits.
4. **Manual drift recovery** — SSH debugging at 2 AM with no structured remediation record.

## Stage-by-Stage: Before vs. After

### Stage 1 — Day 0: Adding a New Microservice Port

**Scenario**: Devin's new metrics service needs port 9090 open in the EC2 security group.

| Step | Without Bob | With Bob |
|:---|:---|:---|
| Understand the convention | Reads Confluence (stale), asks a teammate | Asks Bob: *"How does the EC2 module configure ingress rules?"* → immediate answer |
| Make the change | Opens a Terraform PR, edits `main.tf` inline (wrong file) | Bob targets [`terraform/ec2/ports.yaml`](../terraform/ec2/ports.yaml) directly — correct file, correct format |
| Wait for review | 1–2 day PR queue | Change applied conversationally, PR generated by Bob in seconds |
| Risk of mistakes | Possible HCL syntax error, wrong resource block | Bob enforces project conventions; no raw HCL authoring needed |
| **Time cost** | **2–3 days** | **< 2 minutes** |

**What Devin says**:
> *"I didn't even know what `yamldecode` was. Bob just knew where the port list lived and added the entry. The PR was ready before I finished my coffee."*

### Stage 2 — Day 1: Vault Credential Hygiene & Pre-Commit Policy Check

**Scenario**: Devin is about to push his changes and wants to be certain he won't fail the CI/CD Sentinel gates.

#### 2a — Vault Dynamic Credentials

| Step | Without Bob | With Bob |
|:---|:---|:---|
| Authenticate to AWS locally | Copies `AWS_ACCESS_KEY_ID` from shared doc or `.env` file | Bob traces Vault dynamic credentials in [`terraform/ec2/main.tf`](../terraform/ec2/main.tf) — zero static keys |
| Key rotation | Manual, irregular, often skipped | Automatic — credentials expire after 15 min TTL, Vault issues new ones on next plan |
| Risk of credential leak | High — static keys in local env, CI logs, Git history | Zero — credentials never touch the repo or CI logs |
| CISO audit readiness | "We try to rotate every 90 days" | Immutable Vault audit log; every lease tracked |

**What changes for Devin**: He stops thinking about AWS credentials entirely. Bob tells him what `demo-role` does, and Vault handles the rest. He runs `terraform plan` the same way — the credential chain is invisible and enforced.

#### 2b — Sentinel Pre-Commit Audit

| Step | Without Bob | With Bob |
|:---|:---|:---|
| Know which policies apply | Read policy docs (often outdated) | Ask Bob: *"Audit my config against sentinel/"* → instant policy-by-policy verdict |
| Test locally | Run `sentinel test` if you remember it exists | Bob runs the check and cross-references config values against policy logic |
| Discover failures | At CI run, 20 min after push | In IDE, before first commit |
| Fix cycle | Push → fail → fix → push → re-run (repeat 2–3x) | Single conversational loop, zero CI failures |
| **CI failure rate** | **~40% of first-push PRs** | **~5%** |

**Three active Sentinel policies Bob validates**:

| Policy | File | What it checks |
|:---|:---|:---|
| Encryption enforcement | [`sentinel/enforce-s3-encryption.sentinel`](../sentinel/enforce-s3-encryption.sentinel) | All S3 buckets must use AES256 server-side encryption |
| Mandatory tagging | [`sentinel/require-tags.sentinel`](../sentinel/require-tags.sentinel) | `Environment`, `Owner`, `Project` tags required on all resources |
| Instance type guardrails | [`sentinel/restrict-instance-types.sentinel`](../sentinel/restrict-instance-types.sentinel) | Dev workloads limited to `t3.micro`, `t3.small`, `t3.medium` |

**What Devin says**:
> *"I used to dread the Sentinel check in CI. I had no idea which policy I'd fail. Now I just ask Bob before I commit and it tells me exactly what passes and what doesn't. My last six PRs passed CI on the first push."*

### Stage 3 — Day 2: Drift Detection & Self-Healing

**Scenario**: Apache (`httpd`) stops running on the production EC2 instance after an unauthorized manual change. Port 80 is unreachable.

#### 3a — Detecting the Problem

| Step | Without Bob | With Bob |
|:---|:---|:---|
| How Devin finds out | PagerDuty alert at 2 AM | Drift detection playbook flags the anomaly; Bob parses the JSON report |
| First action | SSH into instance, `systemctl status httpd`, read logs | Bob reads `/var/log/drift-reports/drift-report-<timestamp>.json` and summarizes the blast radius |
| Scope of check | One service (the one that's visibly broken) | Multi-vector: packages, services, ports, file integrity (AIDE), forbidden tools |
| Documentation | None (someone SSHd, things happened) | Structured JSON audit record from the first moment of detection |

**Drift vectors Bob checks** (from [`ansible/baseline-config.yaml`](../ansible/baseline-config.yaml)):

```
1. Required packages:  httpd, aide, fail2ban, chrony, htop, net-tools
2. Forbidden packages: telnet, rsh, tftp, talk, netcat
3. Services running:   httpd (Apache), fail2ban, chronyd
4. Ports listening:    TCP 22 (SSH), 80 (HTTP), 443 (HTTPS)
5. File integrity:     AIDE database diff for config tampering
```

#### 3b — Remediating the Problem

| Step | Without Bob | With Bob |
|:---|:---|:---|
| Remediation approach | Manual `systemctl restart httpd` or ad-hoc Ansible command | Bob dispatches [`ansible/drift-remediation.yaml`](../ansible/drift-remediation.yaml) with targeted role execution |
| Config validation | Skip it (it's 2 AM) | `apachectl configtest` runs before restart; bad config caught before service attempt |
| Forbidden package cleanup | Not done (not noticed) | Detected and purged as part of the same remediation run |
| Audit trail | None | `remediation-report-<timestamp>.json` written to `/var/log/drift-reports/` |
| Confirmation | Hope it stays up | Bob verifies port 80 is reachable post-remediation and reports zero-drift status |
| **Time to resolution** | **45–90 minutes (human paged)** | **Under 2 minutes (autonomous)** |

**What Devin says**:
> *"The last time Apache went down before we had this workflow, it took 45 minutes to diagnose because we had no idea what else changed on that instance. Now the drift report tells Bob exactly what drifted and Bob just fixes it. I wasn't even paged."*

### Stage 4 — GitOps: Pull Request Generation

**Scenario**: Devin needs to submit a PR for the Prometheus port addition and reference the drift remediation verification.

| Step | Without Bob | With Bob |
|:---|:---|:---|
| Write PR title | Manual, inconsistently formatted | Bob generates: `feat(infra): add prometheus ingress port 9090 & verify drift remediation` |
| List changed files | Manual `git diff` reading | Bob inspects the diff and lists every relevant file change |
| Security verification section | Optional / frequently skipped | Automatically included: Sentinel pass/fail, Vault credential check, instance type compliance |
| Rollback strategy | Often missing from PRs | Generated with explicit steps by Bob |
| Reviewer readiness | Reviewer must run their own checks | PR arrives pre-verified; reviewer trusts the compliance summary |
| **Time to write PR** | **20–30 minutes** | **< 30 seconds** |

## What Devin Didn't Have to Learn

With Bob as his infrastructure co-pilot, Devin shipped features this week without needing to know:

- The difference between `yamldecode()` and `jsondecode()` in Terraform.
- How Vault `aws_secret_backend_role` leases are generated and expired.
- Which Sentinel policy function evaluates `aws_instance` resource types.
- How `apachectl configtest` works or why you run it before `systemctl restart`.
- The Harness PR webhook trigger YAML schema.
- The `/var/log/drift-reports/` JSON schema.

Bob provided governance, context, and execution — Devin provided intent.

> **Devin's declaration of intent** → **Bob's governed, policy-enforced, audited execution**

```
Devin says:                              Bob does:

                                         iteration pattern, stays out of main.tf.

                                         policies, cross-references tfvars, reports PASS/FAIL.

                                         15-min TTL, confirms zero static credentials.

                                         service, purges forbidden packages, writes audit
                                         report, confirms zero-drift status.

                                         verification, risk assessment, rollback strategy.
```
